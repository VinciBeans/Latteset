# 0014 以 Tectonic 为准（Tectonic-first）：新功能的设计与验收基准

- **状态**：已接受（2026-09-17，产品负责人）
- **相关**：[0012](./0012-tectonic-library-form-engine.md)（库形态引擎）、[0005](./0005-latexmk-first-incremental-next.md)（latexmk 起步／增量后续）、[0013](./0013-synctex-in-process-parser.md)（进程内自解析）

## 背景：引擎口径一直在"两形态 × 多引擎"之间摇摆

现状事实（2026-09-17 代码为准）：默认设置是 **`engine = XeLaTeX`** 且 **`tectonic.lib_form = false`**（`crates/latteset-core/src/settings/model.rs`）⇒ **用户默认体验是 XeLaTeX 子进程（latexmk）**；Tectonic 另有**子进程**与**库内嵌**两种形态，由设置面选。

近几项工作反复出现"只对一个形态成立"的情况：**㉞ 流式出图**（只有库形态有捕获表里的 XDV）、**㊷ 同步数据补丁**（只有库形态把主输入记成 `texput`）、**㊸ 悬停公式预览**（片段编译在库形态 174–429 ms，在 xelatex 子进程被 biber 拖到 8.6 s）、**㊹ 导言区 format**（机制在两形态完全不同）。每一刀都要重新论证一次"要不要为另一个引擎也做"，决策成本被反复支付；甚至已经出过一次事故：**㊹ 的侦察全部跑在 `xelatex + mylatexformat` 上**，得出"技术前提不成立"，而目标形态是 Tectonic 库形态 —— 两者的 format 机制根本不是一回事（见下）。

## 决策

1. **新功能的设计基准 = Tectonic**：优先 **库内嵌形态**（我们自持 I/O 层：捕获表、页哈希、内存直喂、注入文件、format 缓存都在这一条线上），其次 **Tectonic 子进程形态**。
2. **其它引擎（XeLaTeX / LuaLaTeX / pdfLaTeX，及 latexmk 驱动）不承担优化适配**：任何优化若与它们**不兼容或行为不同**，**默认退回默认行为** —— 不写引擎专属分支、不加开关、不为它调参。
3. **表现面必须如实**：能力不可用时**显式显示"不可用"**，不得静默失效（这是项目既有纪律，本 ADR 只是把它套到引擎维度上）。
4. **优化 ≠ 兼容（重要边界）**：默认档的正确性与回归**不受本决策影响** —— 报错语义、模板兼容（如 ㉖ 模板自带 latexmkrc）、SyncTeX 可用性等属**兼容/正确性**，照旧要做、要有判据。本决策只免除"让**优化**覆盖所有引擎"的义务。
5. **验收口径**：新功能的**数字判据以 Tectonic 形态为准**；其它引擎只做"默认行为不变"的回归检查，不要求数字对齐。侦察若图方便用了系统 xelatex，必须**显式标注为跨引擎参考**，不得当作目标形态的结论。
6. **本 ADR 不改变用户可见的默认引擎**（仍是 `XeLaTeX` + `lib_form=false`）。"要不要把默认引擎切到 Tectonic"是**另一个独立决策**（牵连零预装承诺、bundle 许可审计、能力缺口清单），需单独拍板、各自留证据。

## 影响：按本 ADR 重新研判的既有条目（2026-09-17 同步更新）

| 条目 | 原口径 | 按本 ADR 重判 |
|---|---|---|
| **㊹ 导言区固化为 format** | 侦察"技术前提未成立"（mylatexformat 加载即 0xC0000005；自写 ini 两次未成功） | ⚠ **该结论只对非目标引擎成立**（证据全部来自 `xelatex + mylatexformat`）。**Tectonic 路线根本没测**，而且机制不同：库形态的 format 趟由 `tectonic-format-<name>.tex`（bundle 提供，**可用 `io.inject` 注入我们自己的源**）驱动，缓存按 `format_file_name(digest, name)` 取，装载侧几乎不用改 ⇒ 恢复为**待侦察（仅 Tectonic 库形态）**，C 回 **4**、P 回 **0.83（P2）**；xelatex 那份证据降级为"非目标引擎的记录" |
| **㊸ 悬停公式预览** | 设计与对照数据覆盖"两形态 + xelatex" | v1 **只对 Tectonic 提供**；非 Tectonic 引擎**不提供**（如实显示不可用），不写引擎分支。`§6.11.8` 那条 xelatex 腿降级为**背景数据**（不作为适配目标）；"最小包加速层"同样限 Tectonic |
| **㊴ 子进程编译通道 / ㊶ 分章并行草稿** | 未指定"并行的是哪个引擎的进程" | 并行通道实现为 **Tectonic 进程**（`tectonic.exe` 或跑库形态的 worker 进程）；**不为 latexmk 设计并行通道** |
| **㉞ 流式出图** | 已如实标注"Tectonic 子进程档不可用" | 与本决策一致，保持不变；补一句：**"库形态专属"是设计选择，不是待补的债** |
| **㊷ 库形态同步数据补丁** | 库形态专属（子进程档本来就正确） | 与本决策一致；作为"Tectonic 专属实现"的范例 |
| **㉖ 模板自带 latexmkrc** | P1（P=1.17） | **不变**（属兼容/正确性：默认档就是 latexmk/XeLaTeX，用户撞上就是真 bug） |
| 侦察与验收方法 | 常用系统 xelatex（方便、快、无需 vcpkg） | 新功能**主判据必须在 Tectonic 形态上测**；xelatex 数字只能当跨引擎参考并显式标注 |

## 后果

**正面**：① 每项新功能只需一条证据链（少掉一半侦察与验收成本）；② 可以放心使用"我们自持 I/O 层"的能力（捕获表、页哈希、内存直喂、文件注入、format 缓存），这些在 latexmk 路径上根本不存在；③ 不再为"另一个引擎的行为差异"付设计税，也不再出现"用错引擎做侦察"这类事故。

**负面／风险**：① **默认档仍是 XeLaTeX** ⇒ 这些优化只对主动切换过引擎的用户可见，"能力不对齐"会长期存在，必须在 UI 与文档上如实标注；② 若将来把默认引擎切到 Tectonic，需要回头补齐本 ADR 免除掉的适配（届时按当时的证据重估）；③ "默认退回默认行为"如果没有**显式提示**，就会退化成静默失效 —— 这条必须在每个功能的验收里点名。

## 回退

本 ADR 只约束"设计与验收基准"，不引入任何运行期机制 ⇒ 回退成本 = 改文档与判据；已落地的 Tectonic 专属实现（㉞ 流式出图、㊷ 同步数据补丁）**不需要改动**。
