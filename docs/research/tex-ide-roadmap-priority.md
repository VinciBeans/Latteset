# TeXPresso Roadmap 优先级排序（基于市场痛点调研）

> 状态：**可执行排序（首版）**，2026-09
> 依据：[tex-ide-pain-points.md](./tex-ide-pain-points.md)（总览）+ [desktop](./desktop-latex-editor-pain-points.md) / [online](./online-latex-editor-pain-points.md) / [vscode](./vscode-latex-workshop-pain-points.md) 三份专项
> 现状基线：[design.md](../design.md) §后置/未决清单、[modules.md](../modules.md) §12、[ADR-0005](../adr/0005-latexmk-first-incremental-next.md)、[cli-mcp-plan.md](../cli-mcp-plan.md)
> 说明：本文件是**排序建议**，不是承诺排期；W/D/C/V 打分与分档阈值均为 `[推断]`，可被推翻，但每项都标了可溯源依据。

## 0. 结论速览

| 档 | 项 | 一句话理由 |
|---|---|---|
| **P0** | ① 中文文件名/路径与编码实测复核 ② 首次打开即用（引擎/编译链/字体自动推断） ③ 性能基准与回归基建 ④ 错误诊断升级 ⑤ SyncTeX 可靠性加固 | 全是"高痛点 + 低成本或可自动化验证"，且集中在 TexPresso 已经押注的三条线上 |
| **P1** | ⑥ CLI + MCP 接口 ⑦ 大文档编辑器侧性能 ⑧ 跨文件 LaTeX 语义操作 ⑨ LSP 集成 ⑩ 深色主题 ⑪ 预览滚动/缩放保持 | 差异化高或痛点高，但成本或验证难度上了一个台阶 |
| **P2 / 后置** | ⑫ TinyTeX 捆绑 ⑬ AI 集成 ⑭ 拼写检查 ⑮ 多窗口多项目 ⑯ 外部查看器 ⑰ 自动更新 ⑱ 代码签名 | 有价值但成本/验证代价大，或与当前定位关联弱 |
| **不做** | 实时协作 ｜ 增量编译 ｜ 自研 PDF 渲染引擎 ｜ 自研完整 LaTeX AST | 定位冲突、已被证伪、或投入产出不成立 |

> **一句话路线**：先把「中文 + 首次打开 + 可测量」这三件低成本高价值的事做扎实，再攻「大文档性能 + 跨文件语义」两块硬骨头，协作类明确放弃。

## 1. 评分模型

四项 1–5 分，**分数越高＝该维度越强/越贵**：

| 维度 | 含义 | 打分依据 |
|---|---|---|
| **W** 痛点权重 | 该痛点在市场中的频率 × 严重度 | 来自调研的量化信号（issue 数、SE 票数/浏览量、来源数） |
| **D** 差异化 | 相对竞品能否形成壁垒 | 5＝竞品结构性做不到；3＝大家都有但可做得更好；1＝无意义 |
| **C** 实现成本 | 工程投入 | 5＝数月/高风险；4＝数周；3＝1–2 周；2＝几天；1＝小时级 |
| **V** 验证难度 | 能否证明"真的做好了" | 5＝需干净机器/多人/长期；3＝需真机交互；2＝可脚本化；1＝单测即可 |

**优先级分**：`P = (W + D) / (C + V)`

**分档阈值**（人工微调处均注明）：

- **P0**：`P ≥ 1.3` **且** `W ≥ 4`（高痛点、性价比好）
- **P1**：`P ≥ 0.9`
- **P2 / 后置**：`P ≥ 0.6`
- **不做**：`P < 0.6`，或与产品定位直接冲突、已被证伪

## 3. P0 详述（本批次启动）

### ① 中文文件名/路径与编码实测复核 —— ✅ **已完成（2026-09）**
- **结论**：**路径层面的中文全链路可用**（无需适配）；**实测中发现并修复了一个真实缺陷，但它在日志编码而非路径**。
- **实测**（TeX Live 2026 / CP65001 与 CP936 双代码页）：`latexmk` 编译 exit 0；`tmp/` 中文名产物齐全；**App 真机**打开中文工程 → notify 监视注册成功 → 编译 → 项目根产出 `中文主文件.pdf`（40,648 B）；`synctex view/edit` 中文绝对路径双向通过，且**字节级确认 synctex stdout 恒为 UTF-8**（与代码页无关，故 `from_utf8_lossy` 用法正确）；`.log` 中文文件名可解析出行号。
- **修复的缺陷**：GBK 源文件经 **`pdflatex`** 会让 `.log` 含非法 UTF-8（实测 73 字节，xelatex 则会自行替换）→ 严格读取失败 → 「编译失败」退化为「拿不到任何错误信息」。已加 `log_parser::decode_log`（严格优先 / lossy 兜底）+ `FileSystem::read_to_string_lossy`，`runner` 读日志改走它。
- **产出**：`crates/texpresso-core/src/unicode_path_tests.rs`（7 例）、`log_parser::decode_tests`（3 例）、src-tauri 中文用例（`fs_impl`/`runner`/`storage`/`commands`，含 2 个需 latexmk 的集成用例）、[troubleshooting.md](../troubleshooting.md) 实测记录、[modules.md](../modules.md) §12 条目。
- **验证**：`cargo test -p texpresso-core` **119 通过**；`cargo check -p texpresso --tests` 通过；`npm run build` 通过；**App 端到端**（`中文GBK工程`，pdflatex + GBK 子文件）dev stdout 实测 `编译失败：已从 .log 解析出错误条目 count=9`——修复前该路径错误列表为空。
- **遗留（不计入已完成）**：pdf.js 经 asset 协议渲染中文路径 PDF 的**目视确认**（本会话无 MCP 工具）；编辑 GBK 源文件（`read_file` 仍严格 UTF-8）——已作为独立项记录，未纳入本次范围。

> 原计划内容（保留备查）：在 Windows 真机用中文文件名、中文目录、中文用户名、含空格路径四组样本跑通「打开 → 编译 → 预览 → SyncTeX」；把失败点固化为 e2e 用例。

### ② 首次打开即用（引擎/编译链/字体自动推断）
- **痛点**：P9 模板开箱即用 + P7 中文字体。用户下载学校/期刊模板"没做任何操作就报错：cls 未找到"。
- **做什么**：打开项目时自动推断引擎与编译链——检测 `\documentclass`/`ctex`/`fontspec`/`biblatex`/`minted`（需 `-shell-escape`）/`subfiles`；缺失宏包给出可操作的提示；中文字体探测（`ctex-fontset-windows` 与系统字体可用性）。
- **DoD**：给 3 个真实模板（ctexbook 中文论文、IEEEtran、biblatex 论文）零配置打开即可编译成功；推断结果在 UI 可见且可覆盖。
- **验证方法**：把模板固化为 `test_file/projects/` 下的工程，纳入 e2e。
- **风险**：推断规则会随模板千奇百怪而长尾化，需要"规则 + 手动覆盖"双轨，不能只靠启发式。

### ③ 性能基准与回归基建
- **痛点**：P5。当前 `test_file/projects/benchmark/` 在 [design.md](../design.md) 里标注**未提交**——意味着所有性能结论都无法回归。
- **做什么**：把基准工程落库（小/中/大/多文件/重图五档）；把"冷编译、增量编译、PDF 重载（fetch/parse/render）、端到端延迟"写成可重复脚本，对照 [design.md](../design.md) §延迟预算输出报告。
- **DoD**：一条命令产出延迟报告；超预算时 CI 或本地检查能标红。
- **验证方法**：脚本化（V=2），无需人工判定。
- **风险**：基准工程体积/许可；大文档样本需要自己合成（不可直接分发他人论文）。

### ④ 错误诊断升级（.log → 原因/修复建议）
- **痛点**：P3，全调研最高频。现有实现是"解析 + 同源去重 + 点击跳转"——**及格线**，不是差异化。
- **做什么**：在现有 log_parser 上叠加「错误归类 + 人话解释 + 修复建议」：常见错误模式（缺宏包、未定义控制序列、括号未闭合、字体缺失、biblatex 未跑、`Emergency stop`）映射到可执行建议；错误行号尽量指回**用户源码**而非宏包内部。
- **DoD**：一个真实错误样本集（≥20 例）里，≥80% 能给出"原因 + 改哪一行 + 怎么改"；不能解释的降级为原文 + 行号。
- **验证方法**：样本集快照测试（V 可降到 2–3），再真机点击跳转验证。
- **风险**：Tex 错误本质无结构化输出，覆盖率会是长尾问题——需要持续喂样本，而非一次做完。

### ⑤ SyncTeX 可靠性加固
- **痛点**：P4，行业级长期缺陷（148 issue + 327 SE 题；LaTeX Workshop 官方承认外部查看器 SyncTeX 已不工作）。
- **做什么**：覆盖多文件/`\include` 嵌套、beamer、未加载页、大文档坐标偏移；`synctex(busy)` 文件竞争的重试；正向定位失败时的降级提示。
- **DoD**：multifile + beamer + 大文档三组样本的正反向定位成功率与"跳到位"比例记录在案；已知失效场景有明确提示。
- **验证方法**：真机交互 + 少量自动化断言（PDF 目标页/高亮元素存在）。
- **风险**：部分失效在引擎/坐标语义层，TexPresso 只能做到"尽力 + 诚实提示"。

## 4. P1 详述

### 4.1 ⑥ CLI + MCP 接口（P1 首位，人工上调）
- **理由**：分数 1.60 但 W=3，按阈值本不属 P0。**人工上调到 P1 首位**，因为它同时是三件事：差异化能力（Agent 可直接驱动）、e2e 基建（自动化验证 P0 各项）、以及 [cli-mcp-plan.md](../cli-mcp-plan.md) 已有的落地顺序。
- **依赖**：③ 性能基建的脚本化能力可复用。

### 4.2 ⑦ 大文档编辑器侧性能
- **痛点**：desktop 报告结论——这是"当前最大的可攻占缺口"。引擎层单遍重排是上限，但**编辑器侧不全量重算**是自己能做的。
- **做什么**：语法高亮/大纲/补全改为增量；大纲刷新按 [modules.md](../modules.md) §12 记录的三个方向优化（仅结构文件变化才刷新、内容 hash 缓存、低频节流）。
- **依赖**：③ 的基准工程。

### 4.3 ⑧ 跨文件 LaTeX 语义操作
- **痛点**：P10。VS Code 明确缺失（跨文件改 label/citation key、章节重排），因为它底座是正则静态解析。
- **做什么**：项目级 label/cite key 重命名（含引用点同步）；章节重排；宏感知的包含关系解析（在根文件探测上补一层）。
- **依赖**：与 ⑨ LSP 集成共享索引层——**建议 ⑧⑨ 合并成一个"语义层"里程碑**，避免建两套解析。

### 4.4 ⑨ LSP（texlab）集成
- **痛点**：P8。补全/引用补全是从 2015 年就被提的长期需求。
- **注意**：design.md 已写"monaco-languageclient 需专项研究"——先做技术验证再排期。

### 4.5 ⑩ 深色主题
- **痛点**：配置类第一痛点（206 票 / 230,010 浏览）。成本低（Candy Desk 已有色系），是**性价比最高的体验项**。
- **注意**：Monaco 主题 + 自研 Monarch 高亮 + pdf.js 反色需一起调，否则会出现 TeXstudio 那种"主题不统一"。

### 4.6 ⑪ 预览滚动/缩放保持
- **痛点**：P11。LaTeX Workshop 官方承认刷新会"丢失滚动位置、潜在文件损坏"——TexPresso 已做虚拟化，但滚动位置保持仍需显式保证。

## 5. P2 / 后置

### 5.1 ⑫ TinyTeX 捆绑（人工下调说明）
分数 1.00 落在 P1，但 **C=5 / V=4 全表最高**：下载源与镜像、体积、许可证、代理环境、干净机器验证都是独立课题。建议作为**独立里程碑**，不与本批次混排。它直接解决 P1（最高频入门门槛），一旦做成是强差异化——值得做，但要单独排。

### 5.2 其余后置项
⑬ AI 集成（无一手需求证据，先观察）、⑭ 拼写检查、⑮ 多窗口多项目、⑯ 外部查看器、⑰ 自动更新、⑱ 代码签名。

## 6. 明确不做（否决项）

| 项 | 理由 |
|---|---|
| **实时协作** | P=0.40；在线方案护城河，本地方案投入产出不成立。定位为「个人 / 离线优先」，协作交给 Git（恰是 Overleaf 官方承认做不好的地方）。 |
| **增量编译** | [ADR-0005](../adr/0005-latexmk-first-incremental-next.md) 已实测证伪：latexmk 增量＝整份单遍重排，属 xelatex 引擎上限。 |
| **自研 PDF 渲染引擎** | pdf.js 已是够用的底座；LaTeX Workshop 的教训是"预览是二等公民"，不是"必须自研渲染器"。 |
| **自研完整 LaTeX AST/解析器** | 先复用 texlab/现有解析能力；⑧⑨ 的语义层要建立在可维护的索引上，而不是重写 TeX 解析。 |

## 9. 不确定性与待补数据

1. **W 打分是二手推断**：调研全部来自公开社区数据，**没有一手用户访谈/问卷**。若要做真实取舍，建议先补 5–10 个目标用户（研究生/Git 型作者）的访谈。
