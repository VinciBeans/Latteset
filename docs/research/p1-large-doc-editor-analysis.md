> 上游：[roadmap](./tex-ide-roadmap-priority.md) §3（⑦ 已拆成 ⑦a/⑦b/⑦c：⑦a 大纲增量已落地，⑦c 多文件大项目待测，见该文 §6.2）、[desktop 调研](./desktop-latex-editor-pain-points.md) 痛点 2、[modules.md](../modules.md) §12.1
> 证据约定：**实测** = 本机真机跑出的可复现数字（方法见 §2）；**[推断]** = 未实测的判断；**未测** = 明确没测。
> **结论一句话**：竞品那些"架构性卡顿"我们**结构上不成立**——每击键开销实测 0.02–0.05ms 且**不随文档规模增长**（5405 行/462KB 与 16213 行/1.36MB 同量级），"未闭合 `$` 导致全量重词法"的假设被证伪；真正随规模增长、又落在交互期的只剩两处：**折叠提供者全量扫描**（2.2 → 3.7ms / 次重算）与**每次编译成功后的全量大纲重扫**（52 → 91ms / 次）。→ ⑦ 的 **C=4 偏高**，建议拆成 ⑦a（大纲增量，C2）/ ⑦b（折叠增量，C3，缓做）/ ⑦c（多文件大项目，先建夹具）。

## 0. TL;DR

## 1. 市场症状 → 我们的架构

调研把"大项目性能崩塌"归因为**架构性**：*(a) 编辑器侧的语法高亮/补全/结构解析是全文档甚至全项目同步计算；(b) 编译侧没有真增量*。我们的实现恰好在这两条上都做了不同选择：

| 归因 | 竞品做法（调研原文） | 我们的做法 |
|---|---|---|
| 高亮 | 全文档同步计算 | Monaco Monarch：**逐行 + 惰性 + 状态缓存**；改动只重算受影响区间（本次实测未闭合 `$` 也未触发全量，见 §3.5） |
| 补全 | 静态 cwl 词典 + 与主线程耦合 | 90 条静态片段表 + 前缀过滤（实测 0.02ms），不做跨文件推导（那是 ⑧⑨ 的范围） |
| 结构解析 | 编辑器进程内解析全项目 | 大纲/根文件/include 图**在 Rust**（`core::outline`），前端只提交缓冲与展示结果 |
| 打开大项目 | 一次载入并处理全部文件 | 标签按需打开；文件树只列目录（`list_dir`），内容修改**不**重建树（`refreshTreeDebounced(structural=false)` 直接跳过，`stores/project.ts:31-39`） |
| 编译 | 每次编辑整份重跑 | 编辑期 Quick 单趟 + 空闲收敛（㉘，实测省 40.2%）；真增量属引擎上限（ADR-0005） |

→ **⑦ 的 W=5 是"市场症状权重"，不等于"我们也有同样的病"**。W 仍应保留（用户在意大文档体验），但 C 需要按实测重估（§6）。

## 2. 测量方法（可复现）

- **环境**：本机 Windows / 24 硬件线程 / `devicePixelRatio=1.5` / WebView2；项目 = ③ 的 `test_file/projects/bench/large/main.tex`（451KB / 5405 行）复制到临时项目 `_perf-large`（已删除），再在会话内把它放大到 **1.36MB / 16213 行**复测。
- **驱动**：`npm run tauri dev` 真实窗口 + tauri server MCP（`webview_execute_js`）。
- **不改产品源码**：用 `performance.getEntriesByType('resource')` 取出 Vite 已加载模块的 URL，再 `await import(url)` 拿到**同一 module 实例**（Monaco / `src/latexSuggest.ts` / `src/services/ipc.ts`），从而直接调用：
  - `editor.trigger('keyboard','type',{text:'x'})`（走完整编辑管线 + 我们的 `onDidChangeModelContent`）
  - `latexFoldingProvider.provideFoldingRanges(model)` / `latexCompletionProvider.provideCompletionItems(...)`
  - `ipc.getOutline(buffers, files)`（真实 IPC + Rust 解析往返）
- **指标**：同步 300 次击键的**中位数**（顺序受控 A/B：带我们监听的编辑器 vs 同内容、同语言的**裸 Monaco** 编辑器，各 3–5 轮交替，预热丢弃）；rAF 帧间隔；`PerformanceObserver('longtask')`。
- **方法上的两个坑（记录以免复读）**：
  1. **顺序偏差**：第一轮 A/B 差 0.47ms，交替 3 轮后差值掉到 0.05–0.11ms——首轮差主要是 JIT 预热。**单轮 A/B 会高估自己的开销 5–10 倍。**
  2. **不能用 `slice()` 代理 `getValue()`**：V8 的 `slice` 是 SlicedString（O(1) 视图），实测 0.000ms，完全不能代表 Monaco 的物化成本；用 `join` 平铺代理才有意义（0.19ms/462KB）。真机上 `model.getValue()` 实测 **0.01ms**（活动模型命中缓存）。
- **做不到的**：MCP 的 `webview_keyboard type` 打不进 Monaco（0.56 用 EditContext，`textarea.ime-text-area` 是 `readonly` 且 `aria-hidden`），合成 `input`/`execCommand` 均无效 → 本次用 `editor.trigger('keyboard','type')` 等价路径（少一层浏览器输入管线）；主观"手感"评分**未做**。

## 3. 实测数据

### 3.1 每击键成本（核心结论）

同步 300 次击键中位数（A = 真实编辑器含我们的监听，B = 同内容裸 Monaco）：

| 文档规模 | A（含我们的处理） | B（裸 Monaco） | **我们的净开销** |
|---|---|---|---|
| 462KB / 5405 行 | 0.149ms | 0.101ms | **≈0.05ms** |
| 1.36MB / 16213 行 | 0.126ms | 0.107ms | **≈0.02ms（噪声内）** |

→ **每击键开销不随文档规模增长**（Monaco 编辑 O(log n)；我们的处理是 O(1)：`getValue()` 0.01ms + 一次响应式 `Map.set` + 一个 watcher）。

异步（每键等一帧，含渲染与惰性词法）40 键连续输入 @462KB：`perKey≈6.1–6.8ms`、帧间隔 `p50 5.7–6.3ms`、`p95 9.6–10.3ms`、`max 14.3–15.9ms`（≈1 帧 = 6.9ms @144Hz）→ **没有掉帧证据**；`longtask` 观测为空。

### 3.2 打字期的周期性成本：折叠提供者（随规模增长）

| 文档规模 | `provideFoldingRanges`（我们的全量扫描） |
|---|---|
| 462KB / 5405 行 | **2.2ms**（5 次：2.2/2.2/2.2/2.1/2.2） |
| 1.36MB / 16213 行 | **3.6–4.2ms**（5 次：3.9/3.6/4.2/3.7/3.7） |

旁证：`editor.foldAll` 首次 3.5ms、再次 0.3ms（缓存）→ 3.5ms 里约 2.2ms 是我们的提供者，其余是折叠模型构建。
**频率**：Monaco 的折叠模型在 model 变更后按 `languageFeatureDebounceService`（min 200ms，随提供者耗时自适应上调）重算——**不是每击键，而是打字过程中周期性触发**。
**阈值判断**：60Hz 帧预算 16.7ms → 4ms 可接受；144Hz 帧预算 6.9ms → 单帧内塞进 4ms 会明显挤压其余工作（本次 p95 9.6ms 的那几帧很可能就是它）。

### 3.3 每次「编译成功」后的开销：大纲重扫 —— ✅ 已修（⑦a）

**修前**：`events.ts:20` 每次 `compile-status.success` → `outline.refresh()`，而 `refresh()` 会把**所有打开缓冲的全文**经 IPC 送给 Rust，Rust 再重读/重解析整张 include 图。

| 场景（修前，单文件工程） | `ipc.getOutline` 往返实测 |
|---|---|
| 462KB（1 个缓冲） | **52–56ms** |
| 1.36MB（1 个缓冲） | **91–94ms** |
| 462KB × 8 个缓冲（模拟多文件项目，7 个路径不存在） | 133ms |
| IPC 地板（`get_project` / `list_dir` 空项目） | 2.5ms |

**修法**（三处，互相独立）：① core `OutlineCache` 按**内容指纹**复用未变化文件的扫描结果（内容每次仍重取，外部改动不会被钉住）；② 前端只提交**变化过**的缓冲 + 当前标签集合（`lastSent` 差分；`open_paths` 让后端淘汰已关闭文件的缓冲）；③ 刷新**合并**（进行中只记"待补一次"）。

**修后复测**（11 文件 / 436KB 多文件工程，真机）：

| 场景 | 实测 |
|---|---|
| 全推 11 缓冲 + 全部重扫（≈修前的形态） | **55.5ms** |
| 全推 11 缓冲 + 缓存命中（0 重扫） | **23.3ms**（扫描成本 ≈32ms） |
| 全量提交 5 个缓冲（226KB） | 17.1ms |
| **增量提交 1 个缓冲**（45KB，编辑一个文件） | **9.7ms** |
| **无变化 0 个缓冲**（空闲收敛那一次） | **8.4ms** |
| 地板（0 载荷：IPC + 读 11 文件 + 指纹 + 响应） | 7.9ms |

**真机端到端证据**（真机窗口，编辑 `c01.tex` 一个 `\section` 后自动保存 → Quick 编译 → 空闲收敛 Full 编译）：

- 后端 tracing：`scans=1 reused=10`（Quick 成功后）→ `scans=0 reused=11`（Full 收敛后）；
- 前端 IPC 载荷（拦截 `ipc.getOutline` 实参）：第 1 次 `buffers=1（c01.tex, 44KB）, open=2`；第 2 次 `buffers=0, open=2`；
- 大纲面板同步出现新标题（`真机验证A`），186 个条目结构正确。

**顺带修掉的两个真问题**（都由这次实测暴露）：

1. **入口路径未归一** → 同一文件在 `root_file`（反斜杠）与 include 候选（正斜杠）两种拼写下是两个 key，`visited` 去重失效、大纲可能出现重复项（也违反 `OutlineNode.file` 自己的 DTO 契约）；
2. **并发刷新重复发送**：结构事件风暴里实测连发 11 次刷新、每次都把同一个缓冲重推一遍（并发时谁都来不及写回 `lastSent`）→ 改为合并为「当前 + 补一次」。

**仍然存在**：触发点依旧只有「编译成功」与「结构变化」——**编译一直失败时大纲不更新**。缓存（8–10ms/次）已经让"按保存触发"变得便宜，但刷新时机/节流策略需单独定，记为 [modules.md](../modules.md) §12.1 #17。

### 3.5 被证伪的两个假设（回写以免重走）

1. **"`$` 进入 Monarch 数学态 → 未闭合时每次编辑都要重词法到文件尾"**：❌ 实测不成立。在第 2 行插入一个未闭合 `$`（全文仅此一个，其后 5400 行全处 math 态）后，40 键连续输入的 `perKey 5.78ms / p95 7.1ms / max 8.0ms`，**比闭合状态还略快**。Monaco 的增量词法在该场景下没有退化。
2. **"每击键两次整份 `getValue()` 是随规模增长的主要成本"**：❌ 实测不成立。真机 `model.getValue()` = **0.01ms**（活动模型），每击键净开销 0.02–0.05ms 且不随规模变化。

## 5. 仍然未知（给 ⑦ 定 DoD 前必须补）

1. **多文件大项目**（调研 #4410 的原始症状）：本次只有单文件项目。缺一个"≥20 文件 × 每个数百 KB"的夹具（③ 的档位里 `multifile` 只有 94KB 总量），需要测：打开全部标签的内存与耗时、include 图解析、文件树规模、以及"编译中被 watch 事件淹没"的表现。
2. **`Ctrl+F` / 大范围替换**（Monaco 内置，未测）。
3. **滚动与预览重载**（`PreviewPane` 每次编译整份重新 parse + 渲染）——属 ⑪ 的账，但用户感知的"大文档卡"里它占相当份额，建议 ⑪ 与 ⑦c 共用同一套夹具与口径。
4. **主观门槛**：本次只给了客观代理（帧间隔 / longtask）。"不掉帧"的验收建议定为：`p95 帧间隔 ≤ 1 帧`、`无 >50ms longtask`、`同步每击键 ≤0.5ms@1MB`。

## 6. 建议切分与优先级复核

| 拆项 | 内容 | W | D | C | V | P | 建议 |
|---|---|---|---|---|---|---|---|
| **⑦a 大纲重扫增量** | 只重解析**变化的**文件（include 图索引增量）+ 只提交 **dirty** 缓冲（而非全部）+ 结果缓存；可选把解析放到阻塞池之外 | 5 | 4 | 2 | 2 | **2.25** | ✅ **已完成（2026-09）**：55.5ms → 8.4–9.7ms，见 §3.3 |
| **⑦b 折叠提供者增量** | 由 model 变更增量维护环境栈（或按可见区裁剪）；现在每次重算 O(全文) | 4 | 3 | 3 | 2 | **1.40** | 缓做（未越 60Hz 帧预算；144Hz + 多 MB 才明显） |
| **⑦c 多文件大项目** | 先建"≥20 文件 × 大文件"夹具 + 口径（C1），据数决定是否优化打开/树/内存 | 5 | 4 | 1→? | 2 | 待测 | **下一步**：本次的 11 文件/436KB 只是"多文件"的入门档；打开全量标签、内存、树刷新仍未测 |
| ⑦d 每击键省一次 `getValue` | `EditorPane.vue:137-146` 的重复取值/比较 | 3 | 2 | 1 | 1 | 4.50 | **明确不做**：收益 ~0.05ms，属"分数好看、用户无感" |

**对 ⑦ 原结论的修正**：原表把 ⑦ 记为 `C=4 / P=1.29`，依据是"desktop 报告的最大可攻占缺口"。实测显示该缺口主要是**竞品的架构病**，我们的架构已经规避；剩下的两处是我们自己引入的耦合（F/G），**成本远小于 C=4**。因此：⑦ 不再作为"数周的大工程"整体推进，而是按 ⑦a → ⑦c →（必要时）⑦b 的顺序切；**⑦a 已完成**（大纲增量 + 前端差分 + 刷新合并，见 §3.3），它与 ⑧⑨ 语义层共用同一份 include 图索引的思路仍然成立（`OutlineCache` 就是那份索引的雏形）。
