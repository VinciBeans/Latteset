# 上游「阶段 2」在当前项目上的可行性（引擎子进程 + 流式输出 + 时间片）

> 状态：**实测快照（2026-09）**，本机 Windows / TeX Live 2026。
> 评估对象：[texpresso-live-rendering-roadmap.md](../texpresso-live-rendering-roadmap.md) 阶段 2（该文把这一步称为"**单独就能拿到大约一半的体感收益**"）。
> 姊妹篇：[G2 字节偏移重同步](./g2-byte-offset-resync.md)（页索引这一半）、[DVI/XDV 预览可行性](./dvi-preview-feasibility.md)（渲染那一半，已否决）、[P1-⑦ 大文档编辑器侧性能](./p1-large-doc-editor-analysis.md)（真机探针方法）。
> **结论一句话**：阶段 2 的三件事在我们这里**一件早已有（子进程）、一件结构上不需要（时间片）、只有一件真缺（流式输出）**；缺的那件实测有**三条可用通道**，而且我把它最难的一环做通了——**用"页前缀 + 合成 postamble"在现有 PDF 栈里造出"部分 PDF"**（`xdvipdfmx` 接受，页数正确，首页渲染与完整文件一致）。但原文的验收标准**只满足一半**：UI 不卡 ✅（32s 编译期间每键 4.4ms、零 longtask），"首屏数百毫秒" ❌（实测 ≈1–3s，差 3–10×，除非拥有 DVI 渲染器——那条已否决）。

## 1. 原文对阶段 2 的要求

> **目标**：输出一产生就显示，而不是等编译结束。**这一步单独就能拿到大约一半的体感收益。**
> **做法**：① 用 `socketpair`/管道把子进程 stdout 换成受控通道；② 子进程每写一段输出，主进程立刻追加到内存缓冲并解析；③ 主进程每帧只处理有限的几条消息，然后回到 UI 事件循环。
> **参考**：`fork.c:30`（`socketpair` + `execvp`，含 `dup2(STDERR, STDOUT)` 以免普通输出污染协议通道）；`main.c:176` `advance_engine()`（每帧最多 10 步或 5ms）。
> **验收**：编译一个耗时 10 秒的文档，**第一页应在数百毫秒内出现**，且这 10 秒内 **UI 不卡**。

拆成可判定的三件事：**子进程**（含受控输出通道）、**流式解析**（输出一到就解析）、**时间片**（不阻塞事件循环）。下面逐条对现状。

## 2. 现状：三件事分别在哪

### 2.1 引擎子进程 —— 早有，但输出被丢掉

`crates/texpresso-infra/src/runner.rs` 已经是"子进程 + 超时 + 树杀"的形态（Quick 直调引擎、Full 走 latexmk；`kill_tree` 用 `taskkill /T /F`）。**唯一的缺口是输出**：

```rust
.stdout(std::process::Stdio::null())
.stderr(std::process::Stdio::null())
```

引擎的整条 stdout/stderr 流**被丢弃**，我们只在进程退出后解析 `tmp/<stem>.log`。后果有三个（前两个是阶段 2 直接相关的）：

1. **没有实时进度**——编译期间界面上只有"排版中…"，不知道排到第几页；
2. **没有实时错误**——长文档里"第一个错误在第 8 秒出现"，但用户要等到第 60 秒编译结束才看到它（错误列表只在编译结束后一次性刷新）；
3. 失去 latexmk 自己的诊断输出（例如它为什么挂住），㉕ 的超时诊断只能靠 `.log` 里的痕迹。

**修复形态很小**：`Stdio::piped()` + 一个 tokio 读任务逐行解析并 emit 事件。上游用 `socketpair` 是因为它要跟子进程做**双向协议**（`Q_READ`/`A_FORK`）；我们只需要**单向读**，普通管道就够。

### 2.2 时间片 —— 结构上不需要，且有实测

上游需要"每帧最多 10 步/5ms"，是因为**引擎跑在它的进程内**（被 fork 的那个进程就是它自己），排版代码与 UI 共用同一个事件循环。我们的引擎是**独立进程**，WebView2 的渲染线程与它无共享——所以这一条不是"我们做得差"，而是**前提不同**（该文阶段 2 的前提表里没有这一条，它属于它的架构约束）。

实测（真机窗口 + MCP 探针，同一台机器）：

| 场景 | 每键（异步，等一帧） | p50 | p95 | max | >50ms longtask |
|---|---|---|---|---|---|
| **32s Full 编译进行中**（"排版中…"） | **4.42ms** | 3.9ms | 7.2ms | 16.8ms | **0 个** |
| 空闲（同口径复测） | 4.33ms | 4.3ms | 5.4ms | 6.0ms | 0 个 |

rAF 连续采样 2605 帧无中断；预览区在编译期间保持上一版 PDF（3 个 canvas 在场）。
**结论**：CPU 竞争对我们的 UI 无可测影响——**时间片这一条可以从待办里划掉**（若将来把引擎内嵌进宿主进程，才需要把它捡回来）。

### 2.3 流式输出 —— 三条通道，各自的口径

同一份 121 页文档（`xelatex -no-pdf`，编译 1.31–1.47s），三条通道的时间线：

| 时刻 | stdout `[N]` | 日志文件 `[N]` | XDV 完整页 |
|---|---|---|---|
| 696ms | 6 | （见坑） | 8 |
| 823ms | 22 | 23 | 24 |
| 948ms | 39 | 41 | 42 |
| 1200ms | 81 | 83 | 84 |
| 1451ms | 125 | 125 | 125 |

- **① stdout 页码标记**：与 XDV 完整页**逐点相差 1–2 页**，首个非零都在 ~696ms（占编译 48%）；121 页文档正好 121 个标记。**最便宜**（一条正则，core 里已经有 `pages_typeset()`）。
- **② 日志尾随**：口径与 ① 一致，但**坑**：`tmp/<stem>.log` 是**原地截断重写**的——第一次采样（67ms）读到了**上一轮**留下的 121 个标记。要正确使用必须在"本次编译开始"时重置读取偏移（runner 知道这个时刻，所以可行，但要显式做）。
- **③ XDV 页索引**：最精确（页字节区间 + 页哈希，见 G2 报告），但要解析 4MB 文件（2.7ms/次，可接受），且给的是"**完整页**"而不是"页码标记"。

**粒度**：三条通道都是"**页**"粒度，不是上游那种"字节"粒度；据此我们能做的是"页级进度/页级增量"，做不到"半个页面已经更新"。

## 3. 关键实验：把"页前缀"变成"部分 PDF"

### 3.1 为什么必须做这一步

我们的预览是 PDF + pdf.js。**PDF 只在编译最后一步出现**（`xelatex` 内部在排版结束后才调 `xdvipdfmx`，而 `xdvipdfmx` 需要一个**带 postamble 的完整 XDV**）——所以"输出一产生就显示"在我们的栈里**无路可走**，除非：
- 自研 DVI/XDV 渲染器（[已否决](./dvi-preview-feasibility.md)：产物→屏幕慢 57–68×）；
- **或者**：把编译中的 **XDV 前缀**缝合成一个"看起来完整"的 XDV，交给现成的 `xdvipdfmx` → 得到**部分 PDF** → 交给现成的 pdf.js。

### 3.2 做法（实测有效的最小合成）

1. 解析（G2 的页索引）→ 取前 N 页字节（`pre` 前导 + `BOP…EOP` × N）；
2. **从页内收集字体定义**：原生 `define_native_font`(252) **和** 经典 `fnt_def1..4`(243–246)——两类都必须收；
3. 追一个**从零合成**的 postamble：`post`(248) + 28 字节载荷（`last_bop` = 前缀最后一个 BOP 偏移；`num/den/mag` 取 `pre`；最大高/宽/栈深；**页数 = N**）+ 步骤 2 的字体定义 + `post_post`(249) + 回指 `post` 的指针 + id(7) + `0xDF` 填充。

**关键实测**：
- 最大高/宽/栈深**随便填都行**（`copy`/`zero`/`guess` 三种都转换成功）；
- **字体定义不能少**：只收 252 而漏掉 243–246 会得到
  `xdvipdfmx:fatal: Tried to select a font that hasn't been defined: id=87`（实测：第 5 页选了经典字体 30/33）；
- `post_post` 的回指指针必须改成**新**位置（否则 `Found -1 where post_post opcode should be` / `bop offset … doesn't point to bop command at position -1`——这两个报错很有迷惑性，根因都是"从尾部回溯找 post 时读到了旧指针"）。

### 3.3 结果（121 页文档，不同前缀）

| 前缀 | 页数 | 合成文件 | `xdvipdfmx` | 产物页数 |
|---|---|---|---|---|
| 10% | 12 | 0.42 MB | **647ms** | 12 ✅ |
| 25% | 30 | 1.05 MB | 847ms | 30 ✅ |
| 50% | 60 | 2.14 MB | 818ms | 60 ✅ |
| 75% | 90 | 3.23 MB | 864ms | 90 ✅ |
| 100% | 121 | 4.36 MB | 941ms | 121 ✅ |

- **构建成本 0–4ms**（页索引 + 字体收集 + 拼接），**转换成本 0.65–0.94s 且与页数几乎无关**（固定开销主导：字体加载/初始化）。
- **渲染一致性**：前缀文件第 1 页的 SVG 与完整文件第 1 页**归一化后逐字节一致**，唯一差异是 dvisvgm 的字体编号（`nf0` vs `nf5`）——即几何与字形完全相同。

### 3.4 这带来的形态

```
xelatex -no-pdf（编译中）
   ├── tmp/<stem>.xdv 渐进落盘
   ├── 每 2–3s：页索引 → 取前缀 → 合成 postamble → xdvipdfmx（~0.8s）→ 部分 PDF
   └── 部分 PDF → 通知前端重载 pdf.js（首屏 ≈ 引擎出首页 + 0.8s）
```

**代价与风险**（未测的都在 §7）：额外的 `xdvipdfmx` CPU（每次 ~0.8s，编译期间可能与引擎争抢 IO）；每次刷新都要重载 pdf.js（现状是"重载 + 恢复滚动位置"，即 ⑪ 的机制——**渐进刷新会把这条路径用得很频繁**）；部分 PDF 的交叉引用/目录必然是 `??`（草稿态，与 Quick 单趟的既有语义一致）。

## 4. 验收标准逐条对照

| 原文验收 | 实测 | 判定 |
|---|---|---|
| "编译一个耗时 10 秒的文档，**第一页应在数百毫秒内出现**" | 首屏 = 引擎出首页 + 一次转换 + pdf.js 重载。实测首页可用在编译的 **~48%**（1.31s 文档 → 631–696ms），转换 **0.65–0.9s**，重载 ~0.1s ⇒ **对 10s 文档约 2–3s**（比现状的"编译结束才显示"早 3–5×，但达不到"数百毫秒"） | ⚠️ 部分达成（差 3–10×） |
| "这 10 秒内 **UI 不卡**" | 32s 编译期间：每键 4.42ms、p95 7.2ms、**零 >50ms longtask**，与空闲无差别 | ✅ 达成 |
| （隐含）"输出一产生就显示" | 页粒度可行（§3），字节粒度不可行（要自研渲染器） | 🟡 页粒度达成 |

**为什么达不到"数百毫秒"**：两个必要条件里我们只能满足一个——(a) 引擎必须先在**排版**上走到第一页（实测约编译前半程；纯文本小文档也要几百毫秒），(b) 需要一个能在**几十毫秒**内把这一页画出来的渲染器。我们的 (b) 是 `xdvipdfmx + pdf.js`（~0.7–0.9s），上游的 (b) 是**自己写的 DVI 解释器 + MuPDF**（同进程、无进程启动与字体重载开销）。这再次指向同一个结论：**想要"数百毫秒首屏"，必须拥有渲染栈；而拥有渲染栈的成本已被否决**。

## 5. 建议（按性价比排序）

1. **接上 stdout 管道**（把 `Stdio::null()` 换成 `Stdio::piped()` + 读任务）→ 直接兑现阶段 2 里最便宜、与渲染无关的两件事：
   - **编译期页进度**：core 已有 `pages_typeset()`（`[N]` 正则，现在只用于超时证据）→ 状态栏"已排版 ≈N 页"；
   - **边编译边报错**：对**部分日志**跑 `parse_log`（`.log` 也在渐进写入；stdout 亦可）→ 长文档把"第 60 秒才看到第一个错误"变成"第几秒就看到"。
   **C1**，且不依赖任何未决技术（G2 的页索引只是它的"精确版"，可后置）。
2. **（可选，长文档专用）渐进部分 PDF**：按 §3 的形态做；**只对编译 >5s 的文档开启**——小文档（1–2s 编译）里 0.8s 的转换成本 ≈ 剩余编译时间，纯亏。建议先做 1，再用真实学位论文实测"渐进刷新是否真的改善体感"（并检查 ⑪ 的滚动位置恢复在频繁重载下是否稳定）。
3. **不做**：时间片（不需要）、DVI/XDV 渲染栈（已否决）、字节级增量显示（要有渲染器）。

## 6. 复现方法

```bash
# 三条通道对比（stdout 标记 / 日志尾随 / XDV 完整页）
node <lab>/s2-channels2.mjs <dir> main      # 见 §7：实验脚本为一次性产物，逻辑已在本文复述

# 页前缀 → 部分 PDF（合成 postamble）
node <lab>/s2-synth-post.mjs <file.xdv> <keepPages> <outDir>   # 字体段 collect/none × 尺寸 copy/zero/guess 矩阵
node <lab>/s2-verify.mjs <partial.xdv> <full.xdv>              # 页数 + 首页渲染一致性（shell 重定向，避开沙箱管道限制）

# 成本模型
node <lab>/s2-cost.mjs <file.xdv> <outDir>                     # 10/25/50/75/100% 前缀各自耗时

# UI 不卡（真机）：起窗口 → 点「编译」→ 在编译中跑打字探针（方法同 p1 分析 §2）
```

> 沙箱注意：Node 的 `child_process` **管道** stdio 在本机沙箱下会 EPERM，实验脚本一律用 `stdio: 'ignore'` + shell 重定向落文件。

## 7. 未验证与局限

1. **未验证"渐进刷新"的用户体感**：本文只证明了"能造出部分 PDF"，没做端到端（每 2–3s 刷新一次）的真机体验评估——滚动位置稳定性、pdf.js 重载抖动、以及额外 `xdvipdfmx` 对编译时长的影响都未测。
2. **未在真实学位论文上验证**：hithesis 系被㉖ 阻塞；真实模板的 specials/图片更多，但前缀合成的机制与 specials 无关（只依赖页边界 + 字体定义），**预期**仍成立。
3. **`xelatex` 之外的引擎未测**：`pdflatex` 直接出 PDF（没有中间 XDV，这条路不适用）；`lualatex --output-format=dvi` 未走通。
4. **未测 Windows 上并发 `xdvipdfmx` 与引擎写同一 `tmp/` 的相互影响**（部分 PDF 通常写到另一个临时文件名，但字体缓存/`xdvipdfmx` 的临时文件行为未核）。
5. **进度通道的"日志尾随"实现细节未做**：需要显式的"编译起点重置偏移"，否则会读到上一轮内容（本实验已复现这个坑）。
6. **实验脚本是一次性产物**：本轮为研究写的 `s2-*.mjs` 未入库（结论与命令已在 §6 复述）；若要做正式功能，应把"页前缀 + 合成 postamble"实现进 `texpresso-infra`（进程侧）并在 core 里补单测。
