# 阶段 3「增量输出解析」深挖：验收标准达成，但没有消费方

> 上游依据：[texpresso-live-rendering-roadmap.md](../texpresso-live-rendering-roadmap.md) §阶段 3（"增量输出解析（字节级）"，对应上游 `src/frontend/incdvi.c:86` 的两阶段结构）。
> 姊妹篇：[g2-byte-offset-resync.md](./g2-byte-offset-resync.md)（**全量**页索引这一半）、[dvi-preview-feasibility.md](./dvi-preview-feasibility.md)（渲染那一半，已否决）、[stage2-streaming-feasibility.md](./stage2-streaming-feasibility.md)（流式输出，已落地）。
> **结论一句话**：阶段 3 的技术要件——追加式页索引 + 缓冲区变短的回滚 + **成本 ∝ 新增字节**——已在当前项目**实现并验证通过**（4 种喂入序列对拍全绿，141 轮成本实测增量累计恒定），上游的验收标准「每轮解析耗时常数级」**达成**。但它在当前架构里**没有消费方**：编译期页进度已由阶段 2 的 `[N]` 标记满足、编译后索引只需一次全量（5.4ms）、页级差分的消费方（⑪）尚未开工。故：**原型入库、不接线**（判据见 §8）。副产品更有价值——实现增量时被迫把"页完整"的判据写明确，从而**暴露并修复了全量解析器的两个静默错误**，并把 G2 的"半成品可读"从 6 个采样点加强到 **1122 个截断点 / 71993 页 / 0 处不一致**。

## 1. 上游对阶段 3 的要求（原文口径）

> **目标**：新增输出只解析新增的字节。
> 1. 维护一个 `offset`（已扫描到的字节位置）；2. 只做**指令长度计算**，不解释指令内容；
> 3. 遇到结构标记（DVI 的 BOP/EOP）就记录**字节偏移**进页索引数组；
> 4. **缓冲区变短时**（回滚导致截断）：丢弃最后不完整页，`offset` 退回上一页边界。
> ——"第 4 条是'回滚友好'的关键，一开始就要写进去，后补会很痛。"
> **性能护栏**：让解析成本与**新增字节数**成正比，而不是与**总输出大小**成正比。
> **验收**：长文档编译过程中，每帧的解析耗时应该是**常数级**而非随文档增长。

我们的产物一直是 XDV（`tmp/<stem>.xdv`，每次编译都在），它的页边界是 BOP/EOP —— 与上游解析的 DVI 同一套结构（XDV 是 DVI 的扩展版），所以这四条**逐条适用**。

## 2. 现状：全量那一半早已做透，追加式那半没做

[G2 报告](./g2-byte-offset-resync.md) 已经证明：

- 页包**自包含**（单页切出来补上前导即可独立解析，与完整文件逐字节相同）；
- 全量解析 **4.41MB / 186 页 = 2.72ms**（1.6 GB/s）；
- 截断到任意位置**可读**（当时测了 10/33/50/75/90/99.9% 六个点）；
- 编译期落盘是**突发**的（~0.5MB / ~110ms 一批，共 10 批）。

它明确留下的缺口是（G2 §10-B.8）：**"真正的追加式解析器要维护'已扫描 offset + 跨 flush 的半页状态'"**——也就是本文做的这件事。而 `scripts/xdv-report.mjs --watch` 当时的实现是**每轮全量重解析**（`watch()` 里每轮调一次 `parseXdv`），不是增量。

## 3. 实现：追加式页索引

`scripts/xdv-inc.mjs` → `createIncXdvIndex()`（约 160 行，复用 `xdv-report.mjs` 导出的指令长度原语 `payloadLength`）：

```
状态机：pre → between → inPage → done
  pre     ：还没凑够前导（pre 可能跨多轮）
  between ：页间，等待 BOP（139）
  inPage  ：页体内，只算指令长度；遇 EOP（140）→ 落一页进索引（含页哈希）
  done    ：遇到 post/post_post，收工

每轮 update(buf)：
  ① 若 buf.length < scanned → 回滚：丢弃 eopOffset 越界的页，位置退回"仍完整的最后一个页边界"
  ② 从 scanned 前进到 buf.length；**停在下一条指令的起点**（这样下一轮能无缝续扫）
```

三条实现要点（都不是"照抄就能对"的）：

1. **位置必须停在指令起点**，不能停在"已消费字节的末尾"——否则下一轮会把半条指令当新指令。
2. **边界必须自己校验**：`payloadLength` 对**定长指令**（`set1..4`、`right1..4`…）直接返回长度、不检查缓冲区够不够。全量解析靠"扫过头后 while 自然结束"兜底，增量解析**不能**——越界推进会让下一轮从页中间续扫，**永久丢页**。这是本次实现的第一个坑（对拍直接抓出来了）。
3. **"页完整"的唯一判据是见到 EOP**，不能拿"扫到了缓冲区末尾"代替。

## 4. 验证一：与全量解析对拍（4 种序列）

`node scripts/xdv-inc.mjs <tmp/main.xdv> --selftest`（夹具：`bench/large`，**4.38 MB / 125 页**）：

| 喂入序列 | 轮数 | 结果 | 累计扫描 | 累计耗时 |
|---|---|---|---|---|
| 一次性喂全量 | 1 | ✅ 125 页逐字段一致 | 4.38 MB | 6.4–7.7 ms |
| 按 512KB 分片（≈G2 实测粒度） | 9 | ✅ 一致 | 4.38 MB | 3.8–5.4 ms |
| 按 4KB 细粒度 | **1122** | ✅ 一致 | 4.38 MB | 5.3 ms |
| 回滚（60% → 30% → 60% 再涨满） | 6 | ✅ 一致 | 4.38 MB | 2.9–4.5 ms |

对拍口径是**逐字段**比较 `page / bopOffset / eopOffset / bytes / hash`，且在**每一步**都比（不是只看末态）。

## 5. 验证二：成本 ∝ 新增字节（上游验收标准）

`--cost=<chunkBytes>`：按给定粒度模拟 flush，比较"增量累计"与"每轮全量累计"（同一份 4.38MB 文件）：

| flush 粒度 | 轮数 | 增量累计 | 每轮全量累计 | 扫描字节比 | 耗时比 |
|---|---|---|---|---|---|
| 2 MB | 3 | 6.57 ms（2.19/轮） | 13.73 ms（4.58/轮） | 0.422 | 0.479 |
| 512 KB | 9 | 8.14 ms（0.90/轮） | 27.19 ms（3.02/轮） | 0.196 | 0.299 |
| 128 KB | 36 | 7.95 ms（0.22/轮） | 84.59 ms（2.35/轮） | 0.053 | 0.094 |
| 32 KB | **141** | 7.45 ms（0.053/轮） | 260.55 ms（1.85/轮） | 0.014 | 0.029 |

读法（这就是上游要的"常数级"）：

- **增量累计几乎恒定**（6.6 / 8.1 / 8.0 / 7.5 ms）——它只与"总字节"有关（一次扫描），**与轮数无关**；
- **每轮全量累计随轮数线性增长**（13.7 → 260.6 ms）——成本 ∝ 轮数 × 总字节；
- 每轮耗时：增量 2.19 → 0.053 ms（**随粒度变细而下降**），全量 4.58 → 1.85 ms（受吞吐下界约束）。

**外推模型**（按吞吐推算，[推断]）：全量累计 ≈ `(N/2)·S/v`、增量累计 ≈ `S/v` ⇒ 节省 ≈ `(N/2−1)·S/v`。
代入本夹具（S=4.38MB、N=9、v≈550MB/s）得 ≈ 28ms，实测 19ms，同量级 ✓。
大文档（S=50MB、N=100）⇒ ≈ 4.5s；但即便全量也只有 ~60ms/次 × 100 = 6s，占 4 分钟编译的 2.5% —— **收益天花板不高**。

## 6. 副产品：全量解析器的两个静默错误（已修）

写增量解析器时，"页什么时候算完整"这个问题被迫写明确，于是对拍立刻照出了全量版的两个缺陷（**都在"缓冲区恰好截断在页中间"时触发**）：

| # | 缺陷 | 表现（实测） |
|---|---|---|
| 1 | 页体内 `p += 1 + len` **不校验边界**（定长指令的 `payloadLength` 不检查缓冲区长），越界后靠 while 自然结束兜底 | 8192 字节前缀解出 `4674-8194` 这一页——**页尾越过了缓冲区** |
| 2 | 页完整判据缺失：`while (p < buf.length)` 正常退出（`p === buf.length`）时，与"在 EOP 处正常结束"无法区分 | 12288 字节前缀把 `9350-12287` 当成完整页——**EOP 其实在缓冲区之外** |

两者的后果一样：**"截断前缀"会解出内容被截断的假完整页**，而且它的 `hash` 与完整文件里同名页不同——对一个把"页哈希差分"当判据的机制（⑪）来说，这是**静默错误**（既可能误报"这页变了"，也可能让"半成品页"被当成可用页交给渲染器）。

修复（`scripts/xdv-report.mjs` 的 `parseXdv`）：页体内校验 `p + 1 + len <= buf.length`，并用 `sawEop` 作为页完整的唯一判据。

**修复后的加强验证**（`--prefix=4096`，比 G2 的 6 个采样点强得多）：

```
前缀一致性（每 4096 字节一个截断点，共 1122 点 / 累计比对 71993 页）：
  与完整文件同名页 hash 不一致的页：0
  截断前缀最多解出 124 页（完整文件 125 页）
```

→ G2 的"半成品可读"结论**成立且被大幅加强**；同时说明它当时**只是因为采样点不够密而没暴露上面两个缺陷**（6 个点里没有落在"指令中间"的）。

## 7. 与 SyncTeX 的对拍（补 G2 §9 / roadmap §10-B.9）

新夹具 `_s3-sync`（`bench/large` 的副本，125 页 / 2332 行单文件），两次独立编辑各自编译：

| 样本 | 编辑 | 页哈希差分命中 | SyncTeX（`synctex view -i <line>:1:main.tex`） | 判定 |
|---|---|---|---|---|
| ① 等长替换 | 第 590 行 `typesetting`→`typesetTing`（11 字符，不重排） | **1 页：19** | **Page:19** | ✅ 一致 |
| ② 文首插入 | 第 7 行插入一个词（+11 字符，重排） | **120/125 页**（首个 = **5**，第 6 页恰未变） | **Page:5** | ✅ 一致（首个命中页 = 源码位置所在页） |

读法：**页哈希差分与 SyncTeX 自洽**——⑪ 若用它做"哪些页需要重绘"的判定输入，与"点错误回到源码"用的是同一套页号，不会出现"跳转跳到 A 页、重绘却认为是 B 页"。同时它再次确认 G2 的场景结论：重排会把编辑点之后的页几乎全部作废（120/125），所以⑪ 的 DoD 只能是"**视觉无跳动**"，不能承诺"只重绘一页"。

## 8. 结论：为什么"达成但不接线"

### 8.1 先看上游：它的消费方是谁（2026-09 抓 master 源码核对）

上游 `incdvi.h` 的公开 API 只有 9 个函数，而且**全是"查询/渲染"式（pull），没有任何"页完成回调"**：

```c
incdvi_t *incdvi_new(fz_context *ctx, dvi_reshooks hooks);
void incdvi_reset(incdvi_t *d);
void incdvi_update(fz_context *ctx, incdvi_t *d, fz_buffer *buf);      // 增量扫描（阶段 3 本体）
bool incdvi_output_started(incdvi_t *d);
int  incdvi_page_count(incdvi_t *d);
void incdvi_page_dim(incdvi_t *d, fz_buffer *buf, int page,
                     float *width, float *height, bool *landscape);    // 不渲染就知道页尺寸
void incdvi_render_page(fz_context *ctx, incdvi_t *d, fz_buffer *buf, int page, fz_device *dev);
void incdvi_find_page_loc(fz_context *ctx, incdvi_t *d, fz_buffer *buf, int page);
float incdvi_tex_scale_factor(incdvi_t *d);
```

所以消费方 = **主动调用它的那一层**。顺着 `engine.h` 的 `txp_engine_class` 虚表与 `engine_dvi.c` 的实现（两处都已抓下来核对）可以得到完整链条：

| 环节 | 证据 | 作用 |
|---|---|---|
| 收输出字节 | `engine_tex.c`（`txp_create_tex_engine(..., stream_mode, ...)`） | **流式路径**：收到新字节就 `incdvi_update` ← 阶段 3 验收标准（"每帧常数级"）的对象 |
| 页索引 | `incdvi.c` | 页边界 + 页字节区间 + 页尺寸 + 页定位 |
| 包成统一引擎接口 | `engine.h` 的虚表：`page_count` / `render_page` / `scale_factor` | 三个方法直接由 `incdvi_*` 实现——**incdvi 就是 engine 的"页"能力提供者** |
| 逐页渲染 | `engine_dvi.c` 的 `engine_render_page`：先 `incdvi_page_dim(...,&w,&h,NULL)` 建 `fz_display_list`，再 `incdvi_render_page(..., dev)` | 产出 MuPDF display list |
| 上屏 | `renderer.c`（脏矩形纹理）→ SDL | 只重绘变化区域 |

一个实证细节：**静态查看路径**（`texpresso foo.xdv`）里 `incdvi_update` **只在构造时调用一次**——`txp_create_dvi_engine()` 读完整个文件后 update 一次就返回。也就是说 incdvi 同时服务两种场景：静态查看器（一次喂满）与实时渲染（反复喂）。

⇒ **上游的消费方是它自己的渲染闭环**（engine → 主循环 → renderer）：`incdvi` 不是给外部 API 用的中间层，而是"边编边看"里**从字节流到屏幕的必经段**。这也解释了为什么它值得为"每帧常数级"做优化——它真的每帧被问。

### 8.2 为什么我们没有：四个消费方在别处各有替代

| 上游 incdvi 的用途 | 上游消费者 | 我们的替代 |
|---|---|---|
| 页进度（`output_started` / `page_count`） | 主循环（配合 `advance_engine` 的 5ms 时间片判断"还有没有活"） | 阶段 2 的 `[N]` 标记（日志尾随；比解析 XDV 更便宜，且已在跑） |
| 按需渲染（`render_page`） | MuPDF display list → 纹理 | pdf.js 渲染 **PDF**（我们不在 XDV 上渲染；DVI 渲染已被 [DVI 报告](./dvi-preview-feasibility.md) 否决） |
| 页尺寸/布局（`page_dim`，不渲染即知页大小） | 滚动区总高度、页框 | pdf.js 的 PDF 页尺寸 |
| 滚动/定位（`find_page_loc`） | 视口跳转 | pdf.js `scrollIntoView` + SyncTeX 正向定位 |

⇒ "达成但没有消费方"**不是遗漏，而是架构差异**：我们没有 XDV 渲染栈，页索引因此只剩"离线页级差分 + 诊断"两种用途。若将来真要做"编译期逐页出图"，缺的恰恰是上游这条链的**下游半段**（`render_page`），而它已被 DVI 报告实测否决（比 PDF 链路慢 57–68×）。

把阶段 3 的产出按"谁能用"过一遍：

| 潜在消费方 | 现状 | 需要增量吗 |
|---|---|---|
| 编译期「已排版 N 页」进度 | ✅ **已由阶段 2 的 `[N]` 标记满足**（日志尾随，已在跑） | ❌ 不需要 |
| 编译结束后的页索引 | 一次全量 **5.4ms**（4.38MB 级），编译后只跑一次 | ❌ 不需要 |
| 页级差分（⑪ 的判定输入） | 每次编译后**算一次**差分（~3ms） | ❌ 不需要（不是每帧） |
| 编译期**反复**读页索引（例如每 100ms 刷新的页缩略图 / 页尺寸占位） | **没有这个功能**；渲染那半已被 [DVI 报告](./dvi-preview-feasibility.md) 否决 | ✅ 只有这类需求才需要 |

⇒ **结论：原型与判据都留在仓库里，等真正的消费方出现再接**。触发条件写清楚：*"出现'编译过程中每帧/每 100ms 量级读取页索引'的需求"*（现成积木 = `createIncXdvIndex`，接线成本 = 在 `latteset-infra` 里做一个 Rust 版并挂到 runner 的进度通道上，C2 量级 [推断]）。

反过来说，本次真正的产出是**两件与消费方无关的硬收益**：

1. **解析器的正确性**（两个静默错误已修，前缀一致性从 6 点加强到 1122 点）——它惠及现有的一切页索引用途，包括将来的 ⑪；
2. **对拍基线**（页哈希差分 ⟷ SyncTeX 自洽）——⑪ 开工时可以直接用。

## 9. 复现方法

```bash
# 夹具：任一带 XDV 的工程（本文用 bench/large，4.38MB / 125 页）
node scripts/xdv-inc.mjs test_file/projects/bench/large/tmp/main.xdv --selftest        # 4 种序列对拍
node scripts/xdv-inc.mjs <...>/main.xdv --cost=32768                                    # 成本：增量 vs 每轮全量（141 轮）
node scripts/xdv-inc.mjs <...>/main.xdv --prefix=4096                                   # 前缀一致性（1122 个截断点）
node scripts/xdv-inc.mjs <...>/main.xdv --watch=200                                     # 编译期真实尾随（边编边看）

# SyncTeX 对拍（§7）
cp -r test_file/projects/bench/large test_file/projects/_s3-sync && cd $_
latexmk -xelatex -outdir=tmp -synctex=1 -interaction=nonstopmode main.tex && cp tmp/main.xdv base.xdv
```

## 10. 未验证与局限

1. **外推模型是按吞吐推算的 [推断]**：只有 4.38MB 一个规模的数据点（四档 flush 粒度），没有在"真实学位论文级"（数十 MB XDV）上实测。
2. **未做 Rust 实现**：本文原型是 Node 脚本（用于验证可行性与成本）；接产品要重写成 `latteset-infra` 侧实现，**成本未估**。
3. **增量只覆盖"页索引 + 页哈希"**，不含 `--opcodes` 的指令直方图/specials/fonts 统计（那些是全量扫描的副产品）。
4. **未测"编译中被引擎原地重写"**：XDV 是"写临时名再改名"（§G2 观察），所以"缓冲区变短"的场景在真实编译里未必出现；回滚逻辑是按上游要求实现并用**合成序列**验证的，**没有真实触发样本**。
5. **页号映射只验到"单文件工程"**：`bench/large` 是单文件；多文件工程的页号 ↔ 源码文件映射未做对拍（G2 §3.6 做过一次多文件样本）。
6. **SyncTeX 对拍只有 2 个新样本 + G2 的 1 个**，样本量小；且都用"单趟内容不变/重排"两类编辑，未覆盖"插入导致页数增加"（那会让其后所有页号平移，差分与 synctex 的对应关系需另测）。
